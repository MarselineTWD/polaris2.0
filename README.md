# POLARIS — проектирование устойчивой спутниковой группировки

Веб-сервис для выбора конфигурации низкоорбитальной группировки и оценки
доступности связи северных наземных пунктов со шлюзом.

Сервис рассчитывает положения аппаратов на заданном горизонте, определяет
состав доступных связей, строит сквозные маршруты «наземный пункт → спутники →
шлюз», находит перерывы связи и объясняет их причину, оценивает устойчивость
к отказам и позволяет сопоставлять проектные варианты.

---

## Быстрый старт

### Docker (рекомендуемый способ)

```bash
docker compose up --build
```

Сервис поднимется на <http://localhost:8000>, документация API — на
<http://localhost:8000/docs>.

### Без Docker

Нужен Python 3.11 или новее.

```bash
pip install -r backend/requirements.txt
python run_server.py
```

Адрес тот же: <http://localhost:8000>. Порт и адрес меняются переменными
`POLARIS_PORT` и `POLARIS_HOST`.

### Тесты

```bash
pip install -r backend/requirements-dev.txt
cd backend && python -m pytest -q
```

Ожидается **105 пройденных тестов**. Ключевой из них — `test_parity_geometry.py`:
он сверяет наш расчёт с эталонным модулем организаторов
`Расчетный модуль/geometry.py` (положения аппаратов, состав связей, углы
возвышения) с допуском 1e-9.

## Демонстрационный сценарий

1. **Полная группировка.** Сервис стартует на `01_full_constellation.json`.
   В шапке видно: 48 из 48 аппаратов, 3 плоскости, минимальная доступность
   **96,67 %**. Выберите терминал C70 — доступность 98,75 %, максимальный
   перерыв 2 мин. Проведите по шкале времени: маршрут и связи перестраиваются.
2. **Этап развёртывания.** Нажмите «Этап 1». Доступность падает до
   27,22 / 15,83 / 12,64 %, максимальный перерыв вырастает до 13 ч 16 мин.
   Сохраните оба варианта (**Сравнить → Сохранить текущий**) и сопоставьте.
3. **Отказ аппарата.** Нажмите на аппарат текущего маршрута прямо на сцене →
   «Задать отказ» → «Пересчитать». Маршрут перестроится либо появится перерыв
   с указанием причины.
4. **Изменение проекта.** **Проект** → измените RAAN или фазирование плоскости
   → «Применить и рассчитать». Выгрузите результат кнопкой **Экспорт**.
5. **Ошибка во входных данных.** Загрузите JSON, в котором, например,
   `slot_deg` задан строкой. Сервис назовёт конкретное поле:
   `design.satellites[17].slot_deg`.
6. **Анализ.** **Анализ** → сравнение трёх стратегий маршрутизации, рейтинг
   уязвимых аппаратов, свип точек отказа, автоподбор конфигурации.
7. **Инженерная верификация.** **Анализ → Инженерная верификация** → при
   необходимости «Обновить данные» → выбрать RF, Optical или гибрид →
   «Запустить верификацию». Интерфейс покажет диапазон по трём модельным
   профилям, разложение худшей линии и причины физических ограничений.

### Сверка с эталонным модулем

Расчёт можно проверить напрямую против кода организаторов:

```bash
python "Расчетный модуль/geometry.py" "Данные/01_full_constellation.json" 0
```

и сравнить с ответом `GET /api/runs/{run_id}/snapshot?t_s=0` — формат совпадает
поле в поле.

## Что и как считается

Модель — круговые орбиты и сферическая Земля, без возмущений и увода орбиты.
Константы и формулы взяты из документа «Описание данных».

**Положение аппарата.** `r = R + h`, `n = √(µ/r³)`, `u(t) = slot_deg +
phase_deg + n·t`, далее поворот на наклонение и RAAN. Переход в связанную с
Землёй систему — поворотом на `θ = earth_angle0 + Ω·t`.

**Наземная линия.** Доступна, когда угол возвышения не ниже `min_elevation_deg`
и аппарат активен. Для шлюза дополнительно учитывается его доступность.

**Межспутниковая линия.** Доступна, когда расстояние меньше `isl_range_km` и
отрезок между аппаратами не перекрыт Землёй.

**Активность аппарата.** Участвует аппарат, у которого `launch_batch` не
превышает выбранный `launch_stage` и который не находится в периоде
недоступности. Недоступный аппарат сохраняет расчётное положение, но
исключается из состава связей.

**Сетка времени.** `0, step_s, …, horizon_s − step_s`; правый конец в сетку не
входит. Каждый отсчёт представляет интервал длиной `step_s`.

### Маршрутизация

Граф отсчёта: узлы — активные аппараты, выбранный клиент и шлюзы. Клиентский
пункт является только источником, шлюз — только стоком; наземные узлы трафик не
ретранслируют. Реализованы три стратегии на одном и том же графе:

| Стратегия | Что минимизирует | Зачем |
|---|---|---|
| `min_hops` | число переходов (поиск в ширину) | кратчайший путь, меньше ретрансляций |
| `min_latency` | суммарную длину линий (Дейкстра) | наименьшая задержка распространения |
| `max_margin` | максимизирует минимальный запас линии (широчайший путь) | наиболее устойчив к движению аппаратов |

Доступность от стратегии не зависит — путь либо существует, либо нет;
различаются число переходов, задержка и запас. Это видно в разделе «Анализ».

Поверх стратегии работает **гистерезис**: пока прежний маршрут допустим и не
хуже оптимального более чем на заданный допуск, он сохраняется. Это убирает
дрожание между равноценными вариантами; число перестроений выводится как
отдельный показатель.

**Резервные пути.** После основного маршрута его аппараты исключаются, и поиск
повторяется — до трёх узлонепересекающихся путей. Их число показывает реальный
уровень резервирования.

**Причина отсутствия маршрута** определяется явно:

| Условие | Причина |
|---|---|
| клиент не видит ни одного активного аппарата | нет видимого спутника |
| все шлюзы в периоде недоступности | шлюз недоступен |
| шлюз доступен, но его не видит ни один аппарат | нет контакта со шлюзом |
| обе стороны видят аппараты, но сеть разорвана | разрыв межспутниковой сети |

Для разрыва сети дополнительно считается, какой дальности ISL не хватило,
чтобы соединить компоненту клиента со «шлюзовыми» аппаратами.

### Показатели

По каждому наземному пункту: доля времени радиовидимости, доля времени наличия
сквозного маршрута, максимальный перерыв (длина серии отсчётов × `step_s`),
полный список перерывов с причинами, среднее число переходов, средняя задержка,
число независимых маршрутов и число перестроений. Целевой уровень `≥ 90 %`
проверяется **отдельно для каждого пункта**. Перерывы, упирающиеся в границу
горизонта, помечаются флагом `truncated` и учитываются отдельно.

### Анализ устойчивости

- **Критичные аппараты на отсчёте** — те, чьё удаление разрывает связность
  «клиент → шлюз». Проверяется прямо: аппарат убирается, маршрут ищется заново.
  Если существует два узлонепересекающихся пути, проверка пропускается: в этом
  случае ни один аппарат не является единственной точкой прохода.
- **Свип точек отказа** — полный пересчёт горизонта с постоянным отказом
  каждого аппарата по очереди. Даёт точный ответ «на сколько упадёт
  доступность», а не эвристику.
- **Автоподбор конфигурации** — поиск `raan_deg` и `phase_deg` плоскостей,
  максимизирующих минимальную по пунктам доступность: грубая сетка по
  регулярному (уокеровскому) семейству, затем покоординатное уточнение.
  Каждый кандидат проверяется полным расчётом. На сценарии
  `04_link_range` подбор поднимает минимальную доступность с 62,22 % до
  74,44 % примерно за три секунды.

Состав аппаратов, их `slot_deg` и `launch_batch` при подборе не меняются —
меняется только ориентация и фазирование плоскостей.

## Условия расчёта редактируются осознанно

Раздел `environment` (высота, наклонение, дальность ISL, минимальный угол
возвышения, горизонт и шаг) задаётся загруженным файлом и по умолчанию
**доступен только для чтения**. Так проектные варианты остаются сопоставимыми:
сравнение имеет смысл, когда условия одинаковы.

Исследовать другие условия можно — для этого в разделе «Проект» включается
**исследовательский режим**. Он разблокирует поля и помечает вариант как
посчитанный в изменённых условиях.

Из интерфейса правятся ровно те параметры, которые перечисляет постановка
задачи: очередь запуска, ориентация и фазирование плоскостей, периоды
недоступности аппаратов и шлюзов.

## Архитектура

```
backend/polaris/
  domain/          расчётное ядро, не знает про HTTP
    constants.py     физические константы
    scenario.py      модель cosmo-A-1.0 и валидация с путями до полей
    ephemeris.py     положения аппаратов
    visibility.py    наземные и межспутниковые связи, чанкинг по времени
    routing.py       три стратегии, гистерезис, резервные пути, диагностика
    metrics.py       доступность, перерывы, переходы
    resilience.py    критичные узлы
    analysis.py      свип точек отказа, сравнение стратегий
    optimizer.py     подбор ориентации и фазирования
    recommendations.py  выводы, привязанные к числам
    engine.py        единый проход по времени
    serialize.py     пакет для браузера и выгрузка результата
  research/        отдельный инженерный контур
    external_data.py управляемые снимки Open-Meteo, NOAA, CelesTrak, SatNOGS
    orbit.py          SatKit и явный fallback круговой модели
    link_budget.py    RF/optical budget, погода, Doppler, терминалы
    hazards.py        OMM-screening сближений без ложной вероятности
    engine.py         физический граф и маршруты с запасом в dB
    profiles.py       три демонстрационных профиля оборудования
    store.py          воспроизводимые JSON-результаты инженерных запусков
  api/             HTTP-слой
  store/           SQLite: сохранённые варианты
frontend/
  src/model/       разбор пакета и орбитальная модель
  src/scene/       three.js: Земля, аппараты, связи
  src/panels/      инспектор, шкала времени, проект, сравнение, анализ
```

Расчётная логика и интерфейс разделены: `domain/` не импортирует ни FastAPI, ни
что-либо связанное с HTTP, и полностью покрыт тестами отдельно от API.

### Два контура по времени выполнения

Полный прогон горизонта (720 отсчётов × 48 аппаратов) занимает **60–100 мс**.
Поэтому базовый расчёт выполняется прямо в запросе. Фоново выполняются свип
точек отказа, автоподбор, обновление интернет-снимков и инженерная
верификация; у всех таких задач есть прогресс и кооперативная отмена.

Весь горизонт упаковывается в пакет размером около 35 КБ после сжатия и
уходит в браузер целиком. Перемотка времени, смена наземного пункта и выбор
объектов работают по локальным данным — без обращений к серверу. Запрос уходит
только при изменении конфигурации.

Орбитальная модель продублирована в браузере теми же формулами: расчёт идёт с
шагом 120 с, а картинка обновляется каждый кадр. Совпадение проверено — разница
положений не превышает 1e-10 км.

### Внешние данные и воспроизводимость

Обычный и инженерный расчёт сами в интернет не выходят. Кнопка «Обновить
данные» создаёт в `POLARIS_STATE_DIR/external-data` атомарные JSON-снимки с
временем получения, сроком действия и SHA-256. Если провайдер недоступен,
остаётся последний снимок; без снимка применяется явно отмеченный fallback.

Периоды актуальности: Open-Meteo Weather — 1 час, NOAA SWPC — 15 минут,
CelesTrak — 6 часов, SatNOGS — сутки. Высота Open-Meteo сохраняется без срока.
Все показанные в интерфейсе источники доступны без пользовательской учётной
записи. Экспорт инженерного запуска содержит эпоху, версии моделей, допущения,
метаданные и хеш каждого использованного снимка.

Для синтетических `S01…S48` предполагаются `e = 0` и общий профиль
массы/площади. Три энергетических профиля — демонстрационные, поэтому итог
называется исследовательским диапазоном и не является эксплуатационной или
сертификационной оценкой.

### Формат выгрузки

Кнопка «Экспорт» выгружает CSV в UTF-8 с колонками `schema_version`,
`effective_scenario`, `t_s`, `client_id` и `path`. Одна строка соответствует
одной паре «момент расчёта — наземный пункт» (720 × 3 = 2160 для суточного
горизонта). Версия схемы и полный использованный сценарий со всеми правками
пользователя записываются в первую строку, а `path` хранится как JSON-массив:

```json
{"t_s": 120, "client_id": "C65", "path": ["C65", "S19", "G_MUR"]}
```

Пустой `path` означает отсутствие маршрута. CSV можно повторно импортировать
через панель «Проект»; интерфейс извлечёт из него `effective_scenario`.

Канонический JSON-контракт из задания сохранён на
`GET /api/runs/{id}/export`: он содержит `schema_version` со значением
`cosmo-A-result-1.0`, объект `effective_scenario`, массив `routes`, сводные
показатели, перечень перерывов с причинами и рекомендации.

## Устойчивость самого сервиса

- Валидация повторяет все правила эталонного модуля, но возвращает **список
  всех** проблем с путём до конкретного поля (`design.satellites[17].slot_deg`),
  значением и сообщением по-русски.
- Расчёт по времени идёт чанками: при мелком шаге промежуточные массивы не
  разрастаются, пиковая память ограничена.
- Заданы лимиты на размер запроса, число отсчётов и объём задачи — при
  превышении возвращается понятный отказ, а не падение процесса.
- Расчёт детерминирован, результат кэшируется по хешу содержимого: повторный
  запрос того же варианта обслуживается за доли миллисекунды.
- Сохранённые варианты лежат в SQLite в режиме WAL и переживают перезапуск.
- Необработанные исключения превращаются в `{error_code, message, details}`;
  трассировка остаётся в журнале.
- Если пул процессов недоступен, длительный анализ автоматически переходит на
  последовательный расчёт.
- При недоступном API интерфейс сообщает об этом и продолжает работать на уже
  загруженных данных.
